# 构建项目架构上下文

## 1. 是什么

**项目架构上下文** 是一组描述"这个项目长什么样、怎么组织、有哪些约定"的 Markdown 文档，统一存放在：

```
<projectDir>/.aet/project-analysis/
```

它通过 `aet-analyzing-project` 技能（Skill）自动生成，包含五种典型产物：

| 文件 / 目录 | 内容 | 何时阅读 |
|---|---|---|
| `Overview.md` | 项目概览：技术栈、目录结构、快速开始、测试与环境变量 | 首次进入项目 |
| `Architecture.md` | 系统边界、分层结构、核心流程、模块划分依据 | 理解整体设计 |
| `Modules.md` | 模块分解、依赖关系、模块间通信方式 | 定位某个功能属于哪个模块 |
| `modules/` | 每个模块的**详细分析**（接口、关键流程、设计模式），达到"新人读后能独立改模块" | 在某个模块内做深入修改 |
| `principles/` | 按主题分门别类的**开发原则**（编码规范、错误处理、依赖方向等） | 动手编码 / 重构之前 |

`project-analysis` 目录下还会生成一份 `SKILL.md` 作为"索引 + 使用向导"，列出每份文档的用途和关联模块。

> **与设计库的关系**：项目上下文是"代码事实的固化"，而 `.aet/*_library.yml`（场景库 / 功能库 / SDR 库 / FMEA 库）是"业务知识的沉淀"。两者都是设计流程的**只读真理源**，都通过存在性感知 + 按需浏览接入，**禁止把整个库/整份文档一次性塞进对话上下文**。

---

## 2. 为什么

没有项目上下文时，AI Agent 直接面对一个陌生仓库会踩三类坑：

1. **上下文爆炸** —— 想理解项目就把整棵目录树、整批源码读进上下文，关键信息反而被稀释；
2. **层级识别错误与"编造"** —— 分不清哪些是核心模块、哪些是工具类，凭印象猜测某个功能的归属与约定；
3. **风格/原则漂移** —— 每个模块的编码习惯（命名、错误处理、日志、依赖方向）各不相同，Agent 不了解约定就按通用套路产出，与团队既有架构冲突。

有了项目上下文之后：

- **快而准地导航**：Design / Test / Bugfix 等 Agent 的 prompt 明文规定了"优先读 `<projectDir>/.aet/project-analysis/` 下的 `Modules.md` 与 `Principles.md`"——了解全局结构、对齐既有约定，只需要读几份精炼文档，而不是扫全库；
- **原则成为硬约束**：`principles/` 里的"金律"在需求分析与设计阶段就被执行方吸收，防止"单兵作战"时发明的个人风格与团队约定冲突；
- **代码仍是唯一真理**：上下文文档只是**加速材料**。任何一次需求分析或设计，仍然要求 Agent 去读真正的源码；文档与代码冲突时，**以当前代码为准**。

## 3. 怎么构建

### 3.1 触发方式

构建项目上下文有两种方式：

- **配置向导推荐**：执行 `/aet-init` 完成项目初始化后，向导会询问"是否要分析项目架构并生成文档？"，选择"是"即触发；
- **直接下令**：对 Agent 说"分析这个项目 / 项目分析 / 分析项目架构"，Router 会把请求路由到 `project-analysis` 流程。

### 3.2 两阶段流程

`aet-analyzing-project` 是一个 `pipeline` 技能，按两个阶段顺序执行：

**阶段 1：项目概览分析**（`references/phase1-project-overview.md`，8 个步骤，不可跳过）

```
S0 预检：是否已有 graphify 生成的 GRAPH_REPORT.md（有则跳过 S1，用缓存）
S1 图谱分析：运行 graphify 脚本生成代码知识图谱（节点/边/社区）
S2 探索项目结构：物理目录 + 技术栈配置文件 + 知识图谱导航（God Nodes / 社区 / 隐藏依赖）
S3 深度阅读关键代码：按图谱"看哪里"，再"真正去看"源码
S4 生成 Overview.md
S5 生成 Architecture.md
S6 生成 Modules.md
S7 校验：委派独立子代理验证三份文档（不继承生成阶段的记忆，保证客观）
```

阶段 1 结束后，Agent 会停下来询问：

> "概览分析已生成，可直接使用。下一步将进行更详细的模块分析与原则抽取，是否继续（推荐继续）？"

**阶段 2：组件分析与原则抽取**（`references/phase2-component-analysis.md`，依赖阶段 1 的 `Modules.md`）

```
S1 评估分析深度：对全部模块按优先级分类（High / Medium / Low）
   → 模块数 > 8 时，先把分类结果给用户确认，再决定是否全量分析
S2 并行生成模块文档：委派多个子代理同时分析各模块，产出 modules/ 下的模块文件
S3 校验模块文档：发现问题必须提示用户并修正后才能结束
S4 拆分原则文件：遍历各模块文档的「开发向导」节，结合 Architecture.md 与 Modules.md
   → 按主题聚类拆分到 principles/ 目录（kebab-case 命名，如 naming-style.md）
S5 更新 SKILL.md：如实登记当前已生成的产物与模块索引
```

> **关键约束**：阶段 2 的 `S4` 有明确的抽象纪律——原则必须先有**代码 / 架构 / 模块文档证据**；多模块重复出现的规则优先合并为项目级原则；单模块的习惯不得直接升格为全局标准。这部分也是《需求分析与设计》工作流"自行添加原则"的底座，详见工作流文档的附录。

### 3.3 产物形态

| 阶段 | 产物 | 存放 |
|---|---|---|
| 阶段 1 | `Overview.md` · `Architecture.md` · `Modules.md` | `<projectDir>/.aet/project-analysis/` |
| 阶段 2 | `modules/*.md`（模块详情） · `principles/*.md`（开发原则） · 更新 `SKILL.md`（索引） | 同上 |

### 3.4 使用姿势（重要）

- **当作导航地图，而不是替代品**：读项目上下文只是"先看地图"，真正动手前仍要读对应源码；
- **遵循金律**：编码 / 重构前先读 `principles/` 目录，把其中的规则当成硬约束；如果代码与原则冲突，**以代码为准**并考虑更新原则；
- **周期更新**：项目演进后上下文可能过时。发现文档与实际代码明显不符时，重新跑一次项目分析，或对受影响模块做增量分析。

## 4. 常见问题

| 问题 | 说明 |
|---|---|
| 没有 graphify / 图谱生成失败 | 分析会记录失败原因，改用 `find` / `grep` 等文件系统工具代偿，不影响继续 |
| 模块太多（>8） | 阶段 2 会暂停并把优先级分类给你确认，可选"只分析 High 优先" |
| 文档与代码冲突 | **永远以当前代码为准**；文档仅用于加速理解与对齐约定 |
| 上下文已过时 | 重新运行项目分析，或对受影响模块增量重建 |
