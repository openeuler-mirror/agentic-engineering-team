# 需求分析与设计工作流

## 1. 是什么

需求分析与设计是把"一段原始需求"变成"一份可落地设计说明书"的两段式流水线。全程由 **AET 的 Design Agent**（`/aet:design`）编排，由若干 Skill 承担各阶段职责：

| 阶段 | 承担 Skill | 输入 | 输出 |
|---|---|---|---|
| A. 需求分析 | `aet-req-analysis`（+ `aet-design-env` 工具） | 原始需求 RR + 项目代码库（推荐） | **IR 需求分析说明书**（`type: spec`） |
| B. 需求分析评审 | `aet-req-review`（+ `aet-req-user-review`） | IR + 评审规则 + 动态 checklist | 修订后的 IR |
| C. 功能设计 | `aet-req-design`（+ `aet-fmea-analysis`） | IR + 项目代码库 | **SDD 功能设计说明书**（`type: design`） |
| D. 功能设计评审 | `aet-req-review`（+ `aet-req-user-review`） | SDD + 评审规则 + 动态 checklist | 修订后的 SDD |

下游再消费 SDD 生成开发计划（DPS）并进入实现。阶段间以 Markdown 产物（IR / SDD）作为**契约**，角色间传递的是成品文档而不是长篇口头上下文。

**文档都落在哪里？** 特性（feature）类的设计输出到 `<projectDir>/ai_assistance/features/{feature-name}/design/`，非特性任务输出到 `.aet/{task-id}/design/`，命名形如 `{YYYYMMDD-HHMMSS}-{description}.md`。

---

## 2. 为什么

单个 AI Agent 直接面对"原始需求 → 结构化规格 → 可落地设计"的长程任务时，普遍有四类失效：

| 失效 | 表现 | 工作流的对策 |
|---|---|---|
| **歧义未穷尽就产出** | 需求没搞清楚就机械执行，把假设当结论带进下游 | **Iron Rule**：S1 澄清/场景/分解/功能影响/SDR 全部完成且反演完成标准满足之前，**禁止生成任何文档** |
| **上下文爆炸与漂移** | 整库/整仓库灌进主上下文，关键信息被稀释，越往后越漂移 | SOP 拆分按需加载；模板只经 `aet-design-env` 组装；探索交给子代理只留结论摘要 |
| **层级识别错误与编造** | 一次性吞整棵库树，分不清目录/叶子/功能，凭印象"编造"场景与功能 | `library` 子命令逐级展开 + `-s` 关键词搜索 ≤3 次的硬约束 |
| **一次生成不完备、反复返工** | 复杂任务难一次成形，漏边缘行为与不可行点 | Agent 评审门禁 + 用户门禁双保险（见第 4 篇） |

**价值主张**：分析阶段**只回答 What，不回答 How**（技术栈、架构、模块划分一律不问）；设计阶段每项决策**锚定 IR 与真实代码**；评审不依赖单一自审，而是"独立子代理 + 用户批注"双门禁。规则、流程、检查项全部落盘为可执行的 Skill / SOP / 模板与 checklist，而不是口头约定。

## 3. 怎么用

### 3.1 启动

在支持 AET 的编码 Agent 宿主（OpenCode / Claude Code / xiaoo 等）里执行：

```
/aet:design 我想要做一个……（原始需求）
```

你只需要提供**原始需求（RR）**即可——它可以是 GitHub Issue、产品需求、口头描述、会议纪要或工单。推荐同时把**项目代码库**准备好（供 Agent 建立技术上下文）。

### 3.2 阶段 A：需求分析（你参与的地方 ✅）

整个流程中你可以参与的触点都已标注 ✅，其余为 Agent 自动执行：

| # | 步骤 | 你要做什么 |
|---|---|---|
| 1 | 启动 | 输入初始需求 RR ✅ |
| 2 | **需求澄清（多轮）** | Agent 先陈述"我理解的是…"与"仍不明确的是…"，给出**单批选项化问题**；你只需选择或补充 ✅ |
| 3 | **场景分析** | Agent 基于业务本质识别场景与用例（主成功/备选/异常），请你确认场景与最重要的用例 ✅ |
| 4 | **需求分解** | Agent 输出 FR/NFR 清单、优先级与复杂度评估（Effort），请你确认 ✅ |
| 5 | 功能影响 + SDR 分析（条件触发） | 若项目有功能库/SDR 库且相关技能存在，自动执行 |
| 6 | 生成 IR | Agent 组装模板 → 填充 → 产出 IR（`type: spec`） |
| 7 | **评审（可选）** | Agent 评审门禁，你也可参与人工批注（详见第 4 篇）✅ |

> **注意**：分析阶段 Agent 不会问你"用什么技术栈、怎么拆模块"这类 How 的问题——那属于设计阶段。如果你主动提出实现方案，Agent 会尊重问题域边界，提醒你回到 What。

### 3.3 阶段 C：功能设计（输入必须是 IR + 代码库）

| # | 步骤 | 你要做什么 |
|---|---|---|
| 0 | 材料确认 | Agent 单批索要缺失材料（缺 IR 或代码库会拒绝执行并说明） |
| 1 | **代码仓库探索（深度解剖）** | 代码为唯一真理；委派 1~4 个子代理，只回传高密度结论 |
| 2 | **FMEA 可靠性分析** | 若项目有 FMEA 库，**必须**执行（与 Effort 无关），对照故障模式库四维评估影响/原因/措施/是否新增 |
| 3 | 初稿设计 | 四问框架：代码地基 / 需求映射 / 架构设计 / 运行时分析，产出内存态草案 |
| 4 | 对抗式审查（仅 Effort=High） | 红队子代理按四维攻击面（Fact/Omission/Feasibility/Alternatives）验证，只修订一次 |
| 5 | **设计方案确认** | Agent 总结设计思路，请你确认或反馈 ✅ |
| 6 | 生成 SDD | 模板组装 → 填充 → 产出 SDD（`type: design`） |
| 7 | **评审（可选）** | 同需求分析 ✅ |

### 3.4 Effort 如何影响力度

| Effort | 验证 / 审查力度 |
|---|---|
| Low | 跳过红队验证；评审从简 |
| Medium | 跳过红队验证；维持评审 |
| High | **必须**红队验证、模板全量、完整评审（子代理门禁 + 用户门禁 + 可选复审） |

---

## 4. 三个阶段用户流程一览

```
/design 输入 RR
   │
   ├─→ [A] 需求分析
   │     澄清(多轮✅) → 场景(✅) → 分解(✅) → 功能影响 / SDR
   │     模板组装 → IR ────────────────┐
   │                                   │
   ├─→ [B] 需求分析评审（可选 ✅）     │ 评审后修订 → 输入下一阶段
   │                                   │
   ├─→ [C] 功能设计（必输 IR + 代码库）
   │     材料确认 → 代码探索 → FMEA → 初稿 → 对抗验证(High)
   │     方案确认(✅) → 模板组装 → SDD ─┐
   │                                   │
   ├─→ [D] 功能设计评审（可选 ✅）      │ 评审后修订 → 下游 DPS
   └─→ 评审通过，输出最终 SDD
```

## 5. 常见问题

| 问题 | 处理 |
|---|---|
| Agent 卡在澄清不肯出文档 | 这是 Iron Rule 的正常表现——**歧义未穷尽时，任何文档都是毒药**。配合回答即可 |
| 我没有代码库（全新项目） | 绿色地项目：跳过既有系统分析直接进入设计（`sop-design` 条件分支） |
| 不想参与评审 | 评审阶段**可选**，两阶段的 S3/A4 都可被用户跳过；但建议至少参与设计方案的确认 |
| 需要追溯每条结论的由来 | IR 附录的 `clarification-records` 组件会沉淀每一轮澄清记录，可随时回看 |

## 附录：如何自行添加原则

> 需求分析与设计的"方法论（做什么、怎么做、怎么查）"以 **Skill / SOP / 模板 + checklist / 原则** 四类载体落盘。其中"原则"是**团队可以自行扩充**的开放部分——下面说明格式与添加流程。

### A.1 原则的两种来源

### 来源 1：项目分析自动沉淀

用 `aet-analyzing-project` 构建项目上下文时，阶段 2 的 S4 会自动从各模块的「开发向导」节抽取共性规则，按主题拆分到 `<projectDir>/.aet/project-analysis/principles/`：

```
principles/
├── naming-style.md                 # 命名风格
├── error-handling-principle.md     # 错误处理
├── dependency-principle.md         # 依赖方向
├── skill-writing-principle.md      # Skill 写作规范
└── ...
```

自动抽取有纪律约束：**先有代码证据**；多模块共性优先合并；单模块习惯不得擅自升格为全局标准。

### 来源 2：人工 / 团队显式添加

当团队形成了明确的工程约定（例如"接口变更必须评估兼容性并声明迁移方案""新模块禁止绕过公共接口直连存储"），可以直接在 `principles/` 下新建或修改原则文件——它就是项目的"金律"。

### A.2 原则文件的格式

使用 `assets/principles-template.md` 对应的结构（frontmatter + 固定小节）。**必须遵循的格式契约**：

```markdown
---
project: [项目名]                          # 必填：所属项目
type: development-principle                 # 必填：固定值，表示这是一条开发原则
description: [一句话说明原则的核心思想]       # 必填：2-3 句
base_commit: [git commit hash]              # 必填：该原则依据的代码基线（用于对齐/溯源）
principle_category: [主题分类]              # 必填：见下方分类建议
principle_scope: [project-scoped | category-scoped(适用于哪些类) | module-scoped(适用哪些模块)]
---

# [原则名称]

## 原则详细描述
[动机、依据与含义：为什么这条原则存在，它如何指导设计与实现。]

## 为什么要这样
[设计原因、约束与权衡：不要只说"为了统一风格"，要说明它解决什么问题。]

## 适用范围
- [适用哪些模块 / 场景]

## 规则
- [要遵守它必须满足什么]

## 反模式 / 禁止项
- [哪些做法违反了这条原则]

## 修改检查清单
- [ ] [修改相关代码时要检查什么]
```

### A.3 分类建议

按主题聚类（与自动抽取的分类保持一致）：

| 分类 | 示例 |
|---|---|
| 工程（Engineering） | 错误处理、日志、测试、配置 |
| 架构（Architecture） | 模块边界、依赖方向、扩展点 |
| 写作（Writing） | 文档组织、SKILL 写作、模板用法 |
| 治理（Governance） | 检查清单、变更流程、风险控制 |

文件命名 `kebab-case.md`，文件名直接表达主题（如 `naming-style.md`）。

### A.4 命名与文件放置规范

1. **File name 直抒主题**：`error-handling-principle.md`、`dependency-principle.md`；
2. **按主题聚类，不按模块机械拆分**：同一主题的多条规则合成一个文件；
3. **scope 三档**：仅单模块 → `module-scoped`；一类模块 → `category-scoped`；贯穿全项目 → `project-scoped`；
4. **避免过度泛化**：不要把单个模块的习惯直接升格为全局标准；必须有跨模块共性或明确证据。

### A.5 添加 / 修改后的生效方式

- **新原则写入后**，`principles/` 目录由 `aet-analyzing-project` 的入口文档登记索引。后续任意一轮需求分析/设计/实现前，Agent 都会被引导优先阅读这些原则，并作为硬约束内化；
- **与代码冲突**：原则与当前代码冲突时**以当前代码为准**——此时应审视并更新原则（或标注其适用范围），而不是强迫改造既有代码；
- **版本溯源**：修改原则时同步更新 `base_commit`，让"这条原则基于哪个代码基线"可追溯。

### A.6 一个完整示例

```markdown
---
project: agentic-engineering-team
type: development-principle
description: 接口变更必须显式声明兼容性影响与迁移方案，禁止静默更改对外契约。
base_commit: 105be58
principle_category: Architecture
principle_scope: project-scoped
---

# 接口变更兼容性承诺

## 原则详细描述
任何对外（含跨模块）接口的签名、语义、默认值变更，都必须在设计方案中显式列出
兼容性影响与迁移路径。防止"悄悄改接口"导致的隐性破坏。

## 为什么要这样
变更若静默进行，下游实现与测试无从得知契约变化，会在集成期集中爆炸；显式声明
兼容影响把破坏性变更的探测点前移到设计评审阶段。

## 适用范围
- 所有跨模块接口、外部 SDK、配置文件字段
- 需要 break 的场景（版本升级 / 重构）

## 规则
- 接口变更必须在 SDD 的「接口设计」节列出 old vs new 对照
- 存在破坏性变更时，必须给出迁移方案或版本策略
- 评审 checklist 必须包含“接口兼容性”检查项

## 反模式 / 禁止项
- 在实现中直接改函数签名而不更新设计文档
- 用兼容性理由拒绝必要的重构

## 修改检查清单
- [ ] 是否更新了 SDD 的接口设计节？
- [ ] 是否标明了破坏性变更的迁移路径？
- [ ] 下游模块是否有新增依赖边？
```
