# 围栏机制

> 文档版本：v1.1 | 更新日期：2026-05-27 | 软件版本：v1.1.0

## 概述

围栏（Fence）是 AET 的模块保护机制。每次开发时，Aet-Design 智能体在设计阶段自动划定本次可以改、禁止改和有条件改的文件范围，开发过程中 AI 严格遵守这些边界。

> 工作流控制 Agent 执行顺序和确认点，围栏控制开发时 AI 能改哪些文件。两者是独立的，互不依赖。日常使用 AET 时不需要理解围栏，只有在需要保护核心模块时才需要关注。

### 模块层次

AET 将项目模块按层次组织，围栏的保护规则基于以下层次结构：

| 层次 | 说明 | 示例 |
| :--- | :--- | :--- |
| 表现层 | 用户界面 | UI（界面） |
| 接口层 | 对外 API | API（接口层） |
| 业务层 | 业务逻辑实现 | Evaluation（评估引擎）、Skill（技能管理） |
| 工具层 | 提供通用工具服务 | Parser（流程解析） |
| 基础层 | 核心功能，被其他模块依赖 | Core（数据库与配置）、Auth（认证） |

### 依赖关系

```
┌─────────────────────────────────────────────────────────────┐
│                        表现层 (UI)                          │
└────────────────────────────┬────────────────────────────────┘
                             │ 调用
┌────────────────────────────▼────────────────────────────────┐
│                       接口层 (API)                           │
└───────┬─────────────┬─────────────┬─────────────┬───────────┘
        │             │             │             │
        ▼             ▼             ▼             ▼
┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐
│ 业务层    │  │ 业务层    │  │ 基础层    │  │           │
│Evaluation │  │ Skill     │  │ Auth      │  │           │
└─────┬─────┘  └─────┬─────┘  └─────┬─────┘           │

      └──────────────┴──────────────┴───────────────────┘

                    ┌────────▼────────┐
                    │    基础层       │
                    │  Core / Parser │
                    └────────────────┘
```

## 围栏的工作机制

### 围栏配置

围栏配置包含三种权限，由 AET 在设计阶段自动生成在 SDD（软件设计文档）中：

| 符号 | 含义 | 说明 |
| :--- | :--- | :--- |
| ✅ | 允许修改 | 本次开发可以修改的文件 |
| ❌ | 禁止修改 | 本次开发不能修改的文件 |
| 🔵 | 条件修改 | 满足特定条件才能修改 |

配置示例：

```
✅ 允许修改：
  - src/features/login/
  - src/components/LoginForm.tsx

❌ 禁止修改：
  - src/core/db.js
  - src/core/auth.js
  - src/app/api/*

🔵 条件修改：
  - src/lib/utils.ts（仅在添加日志功能时可以修改）
```

### 三个保护点

围栏在整个开发流程的三个关键点发挥作用：

```
需求分析 → 需求设计 → 开发计划
                           │
                    ┌──────▼──────┐
                    │  保护点 1    │ ← 生成围栏配置（SDD 中）
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   编码实现   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  保护点 2    │ ← AI 开发时自检
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   PR 创建   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  保护点 3    │ ← PR 创建前最终检查
                    └──────┬──────┘
                           │
                      ┌────▼────┐
                      │  合并    │
                      └─────────┘
```

| 保护点 | 位置 | 保护内容 |
| :--- | :--- | :--- |
| 保护点 1 | 开发计划生成时 | 定义允许/禁止/条件修改的文件范围 |
| 保护点 2 | 编码实现时 | AI 对照围栏配置自检，拒绝越界修改 |
| 保护点 3 | PR 创建前 | 提交前最后一次检查，确保没有越界 |

### 模块依赖保护规则

围栏的底层逻辑基于四条架构原则，AET 在生成围栏配置时会自动遵循：

#### 规则一：禁止反向依赖

高层模块不能依赖低层模块，依赖方向必须从上至下。

```
❌ 错误：
  - UI 层直接调用 Core 层（绕过 API 层）
  - 业务层直接操作数据库（绕过数据访问层）
✅ 正确：
  - UI → API → 业务层 → 基础层
```

#### 规则二：禁止跨层调用

只能相邻层次之间调用，不能跳过中间层。

```
❌ 错误：UI → Evaluation（跨过 API 层）
✅ 正确：UI → API → Evaluation
```

#### 规则三：禁止循环依赖

模块之间不能形成循环依赖关系。

```
❌ 错误：
  - Module A → Module B → Module C → Module A
✅ 正确：
  - Module A → Module B → Module C（单向）
```

#### 规则四：保持接口稳定

被多个模块广泛依赖的接口不能随意变更。

```
❌ 错误：修改被广泛使用的函数签名，导致调用方全部报错
✅ 正确：新增函数，保留旧函数（可选废弃，逐步迁移）
```

## 用户操作流程

### 第一步：生成模块依赖分析

仅首次使用或在项目结构发生重大变化时需要执行。

在项目根目录执行：

```
/aet-auto 项目分析
```

AET 会自动分析项目结构，生成模块依赖文档到 `.aet/project-analysis/`：

```
.aet/project-analysis/
├── Modules.md          # 模块清单与依赖矩阵
├── Architecture.md     # 架构概览
├── Overview.md         # 项目概览
└── modules/            # 各模块详细分析
```

这份文档包含模块间的依赖关系，是后续围栏配置的依据。项目结构发生重大变化时（如新增模块、重构），需要重新执行此步骤以更新分析结果。

### 第二步：在开发计划中确认围栏

执行 `/aet-auto <issue-url>` 开始功能开发后，Aet-Design 智能体在设计阶段会自动分析本次需要改哪些文件、不该改哪些文件，并将围栏配置包含在 SDD 中。

当 AET 提示"开发计划已生成，请评审"时，检查围栏配置：

```
AET: 开发计划已生成，请确认围栏配置是否合理。
     ✅ 允许修改：src/features/login/
     ❌ 禁止修改：src/core/db.js, src/core/auth.js
```

如果你觉得不合理，可以直接告诉 AET 调整：

```
用户: 请将 src/config/ 目录也加入禁止修改列表。
AET: 已更新围栏配置。
```

### 第三步：开发时由 AI 自动执行

围栏配置确认后，Aet-Implement 智能体在开发时会自动遵守：

| 情况 | 表现 |
| :--- | :--- |
| 改 ✅ 允许范围 | 正常执行，无需你介入 |
| 碰到 ❌ 禁止范围 | AI 自动阻止，并询问你是否授权突破 |
| 碰到 🔵 条件范围 | AI 自动检查条件是否满足 |

如果 AI 碰到禁止修改的文件，会这样问你：

```
AET: 检测到本次开发尝试修改 src/core/db.js，
     该文件在围栏中标记为 ❌ 禁止修改。
     如需突破围栏，请输入原因申请授权。
```

你可以：
- **拒绝**：回复"不允许修改"，AI 会寻找替代方案
- **授权**：回复"允许修改，原因：需要新增用户表字段"

### 第四步：在评审时回顾

每次开发完成后，可以回顾围栏效果：

- 围栏是否有效保护了核心文件？
- 是否有文件需要补充到禁止修改列表？
- 围栏是否过于严格影响了开发效率？

回顾结果会应用到下一次开发。

## 围栏突破流程

当技术原因必须修改禁止范围的文件时，按以下流程处理：

```
技术原因导致必须突破围栏
           │
           ▼
 说明原因申请放行
           │
           ▼
    ┌──────────────┐
    │   人工审批    │
    └───────┬──────┘
            │
      ┌─────┴─────┐
      ▼           ▼
    拒绝         批准
      │           │
      ▼           ▼
  寻找替代    记录突破原因
  方案         │
              ▼
        同步更新围栏配置
              │
              ▼
           继续开发
```

具体操作步骤：

1. **说明原因**：详细描述为什么必须突破围栏，如"运行时发现模块兼容性问题，必须修改导入方式"
2. **申请审批**：AET 会暂停等待你的确认
3. **记录原因**：将突破原因写入提交信息，供后续追溯
4. **更新配置**：AET 会自动同步更新围栏配置，反映实际修改范围

## 最佳实践

### 设计阶段

- 充分调研：设计前确认本次开发涉及的具体文件和模块
- 评估复杂度：确认"仅复用"的模块是否真的不需要修改
- 明确边界：清晰定义允许和禁止修改的范围

### 开发阶段

- AI 会严格遵循围栏，你不需干预
- 如果 AI 请求突破围栏，仔细评估后再决定是否授权

### 评审阶段

- 检查实际修改的文件是否超出了允许范围
- 评估越界修改对其他模块的影响
- 确认围栏配置是否需要补充调整

## 总结

围栏机制当前的能力和未来演进方向：

| 维度 | 现状 | 演进方向 |
| :--- | :--- | :--- |
| 围栏定义 | 文档级（SDD 中文本描述） | 结构化（独立配置文件） |
| 围栏检查 | AI 开发时自检 + 人工评审 | 自动化检查 |
| 围栏类型 | 允许/禁止/条件三种 | 丰富语义（只读、有限修改等） |
| 突破流程 | 有流程但依赖人工审批 | 自动化审批-记录-同步 |
| 设计准确性 | 部分偏差 | 通过项目分析减少偏差 |

## 常见问题

### 为什么 AI 想改被禁止的文件？

设计阶段可能低估了集成复杂度。例如运行时发现必须修改导入方式才能兼容。这是正常情况，通过授权突破流程处理即可。

### 如何扩展但不修改禁止文件？

使用以下模式：
- 新增函数，保留原函数
- 新增字段，不修改现有字段
- 使用装饰器或中间层隔离变更

### 围栏检查是自动的吗？

AI 在开发时会自动检查围栏约束（保护点 2）。人工评审作为第二道防线，在 PR 创建前确认没有越界修改（保护点 3）。
