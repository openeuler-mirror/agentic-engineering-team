# AET Claude Code Plugin (cc_plugin)

This directory implements the Claude Code adapter (Layer 2 plugin) for the
AET workflow Core, per `新方案.md` §2.3, §4.2 (R8: capability matrix), and
the contract in `AGENTS.md` at the project root.

## Architecture: dual-form plugin

The plugin operates in two complementary modes (AGENTS.md "Plugin 双形态"):

### Passive mode (agent-driven, PreToolUse + PostToolUse hooks)

When the agent invokes `aet workflow ...` via the Bash tool:

1. **PreToolUse** hook fires → handler rewrites the command to append
   `--output json` (idempotent — skipped if already present) and returns
   `permissionDecision: 'allow' + updatedInput`.
2. Bash runs the rewritten command → JSON stdout is captured.
3. **PostToolUse** hook fires → handler parses the JSON, calls
   `resultToCcOutput(result, 'PostToolUse')`, and emits the result as
   `additionalContext` (status banner + `result.prompt` + per-event
   fragments). The agent never sees the raw JSON stdout via the tool
   result — it sees the injected prompt text on the next turn.

If the result's `events[]` contains `omit_prompt`, the handler emits `{}`
and lets the raw tool result pass through unchanged (no native "suppress
CLI return" capability in CC).

### Active mode (user-driven, UserPromptSubmit hook)

When the user types one of the slash commands `/design`, `/implement`,
`/bugfix` (each generated by `aet plugin init` from its workflow id — the
`aet:` namespace prefix is also accepted, e.g. `/aet:design`):

1. **UserPromptSubmit** hook fires (matcher `""`) → handler regex-matches
   the prompt against `^\/(?:aet:)?(design|implement|bugfix)`. If no match,
   emit `{}` (let CC handle the prompt as-is).
2. Run `aet workflow init --name <workflow-id> --output json`. If
   `ok=false` (e.g. UNKNOWN_WORKFLOW), inject the error prompt as
   additionalContext and stop.
3. If `data.status==='workflow_started'`, run `aet workflow handover
   --output json` to enter step 1.
4. Inject the handover result's `prompt` field (step-1 task text) as
   additionalContext. The agent reads it on the next turn and begins
   executing.
5. If `data.status==='intervention_required'` (active workflow already
   exists), inject the intervention prompt and stop. The agent reads it
   and the user decides (continue / discard / cancel).

Subsequent step handovers happen via passive mode: the agent invokes
`aet workflow handover` via the Bash tool, PreToolUse rewrites it,
PostToolUse injects the next step's prompt.

## Capability matrix

Per AGENTS.md "已知 stale 代码" + "Plugin 双形态" — dual-channel design
(Core b3):

| AET event              | CC support    | How |
|------------------------|---------------|-----|
| `prompt.inject`         | supported     | Injected as additionalContext (rarely emitted under b3 — step text lives in top-level `prompt` field) |
| `prompt.inject_system`  | degraded      | Surfaces as `[AET system note] ...` additionalContext (no system-prompt mutation in CC) |
| `context.clear`         | degraded      | Surfaces as a text hint (rarely emitted under b3 — workflow-complete uses `data.status='workflow_complete'` instead) |
| `omit_prompt`           | degraded      | Handler emits `{}` and lets raw stdout pass (no native "suppress CLI return" capability in CC) |
| `interrupt_execution`   | degraded      | Surfaces as an additionalContext warning (no native "halt agent's turn" API in CC) |
| `error`                 | supported (R9)| Always visible — `[AET ERROR <code>] <message>` additionalContext |

Lifecycle metadata from `CommandResult.data` (`workflow_started` /
`step_advanced` / `workflow_complete` / `intervention_required`) is
surfaced as a brief status banner prepended to additionalContext.

Per R9, errors are NEVER silenced in any mode.

## Files

| Path | Purpose |
|------|---------|
| `hooks/handlers/aet_handler.ts` | **Single build entry** — a thin dispatcher: reads the CC hook JSON from stdin, routes on `hook_event_name` to the per-event modules. Bundled to a single `dist/plugins/claude_code/handlers/aet_handler.js` by `npm run build`; the source is split for maintainability. |
| `hooks/handlers/shared.ts` | Shared plumbing: stdin framing, CLI subprocess spawning, output emission, debug logging, build-time defines, Bash matchers. |
| `hooks/handlers/user_prompt_submit.ts` | ACTIVE MODE handler — `/aet-*` slash command → one-shot `aet workflow command-init`, injects the result prompt. |
| `hooks/handlers/pre_tool_use.ts` | PASSIVE (pre) — rewrites `aet workflow <...>` to append `--output json` (and `aet plugin init` to append `--agent`). |
| `hooks/handlers/post_tool_use.ts` | PASSIVE (post) — replaces the tool result's stdout with `result.prompt`; handles `aet plugin init` reload signalling. |
| `hooks/handlers/session_start.ts` | BOOT MODE handler (auto-run `aet plugin init`). Currently **disabled** in the dispatcher. |
| `hooks/settings.json` | CC settings snippet to merge into `~/.claude/settings.json` (registers all 4 hooks pointing at the same bundled handler). |
| `commands/` | Empty by default — `aet plugin init` generates one `<id>.md` per configured workflow / command (`design.md`, `implement.md`, `bugfix.md`, `auto.md`, ...) into the host's commands dir at runtime (see SessionStart/PostToolUse). |
| `json_to_cc.ts` | `CommandResult` → CC `additionalContext` translator (`resultToCcOutput` / `resultToCcPostToolOutput`). |
| `types.ts` | CC-specific type declarations (`CcHookInput`, `CcHookOutput`, `CcHookEventName`, `CcPluginManifest`). Core contract types are imported as `import type` from `src/definitions/events.ts`, not mirrored. |
| `index.ts` | Plugin manifest (install metadata + capability matrix). |

## Install

### Native plugin (recommended)

After `npm run build` (in this repo), a self-contained CC native plugin is
produced at `dist/plugins/claude-code/`. Install by copying it into
your `~/.claude/plugins/` directory:

```bash
cp -r dist/plugins/claude-code ~/.claude/plugins/aet
```

Restart Claude Code. The plugin auto-loads: `hooks/hooks.json` registers
three hooks (UserPromptSubmit + PreToolUse + PostToolUse), all pointing at
`node ${CLAUDE_PLUGIN_ROOT}/bin/aet_handler.js` (no path hardcoding; the
`node ` prefix means the hook works even if the executable bit on the bundle
is stripped when the plugin is copied). The
`.claude-plugin/plugin.json` manifest declares `name`/`description`/`version`.

Verify with `/design`.

### Legacy scatter-install (alternative)

For users who prefer not to install as a native plugin, or who consume
`@aet/workflow-core` as an npm library (handler resolved via
`$CLAUDE_PROJECT_DIR/node_modules/@aet/workflow-core/...`):

```bash
# 1. Register the hooks in CC settings (merge the snippet into ~/.claude/settings.json).
mkdir -p ~/.claude
# (Edit ~/.claude/settings.json to merge hooks from src/plugins/claude_code/hooks/settings.json)

# 2. Copy the 3 slash command files.
mkdir -p ~/.claude/commands
cp src/plugins/claude_code/commands/aet-{design,implement,bugfix}.md ~/.claude/commands/

# 3. Make the handler available. Either install the npm package globally
#    (so $CLAUDE_PROJECT_DIR/node_modules/@aet/workflow-core exists), or
#    copy the bundled handler directly:
mkdir -p ~/.claude/handlers
cp dist/plugins/claude_code/handlers/aet_handler.js ~/.claude/handlers/
# Then edit ~/.claude/settings.json to point the hook command at that path.
```

The native plugin mode supersedes this for end users; scatter-install is kept
for the library-consumption case.

## Usage

### Active mode (user starts a workflow)

In Claude Code, type one of the slash commands:

```
/design        # 2-step: requirements_analysis → requirements_design
/implement     # 3-step: development_plan → implement → verify
/bugfix        # 2-step: diagnose → fix
```

The UserPromptSubmit hook fires, runs `aet workflow init --name <workflow-id>
--output json` + `aet workflow handover --output json`, and injects the
step-1 task prompt as additionalContext. The agent reads it on the next
turn and begins executing.

### Passive mode (agent advances a workflow)

When the agent finishes a step and wants to hand over to the next, it
invokes the CLI via the Bash tool:

```bash
aet workflow handover
```

PreToolUse rewrites it to `aet workflow handover --output json`, Bash
runs it, PostToolUse parses the JSON and injects the next-step task
prompt as additionalContext. The agent never sees the raw JSON stdout.

When the agent calls `aet workflow handover` while on the LAST step,
Core returns `data.status='workflow_complete'` with a completion
prompt — the agent reads it as "all steps done, no further handover".

### Explicit step jumps

Both modes accept `--step <id>` to jump forward (skip) or backward
(redo) explicitly:

```bash
aet workflow handover --step requirements_design
```

## Environment variables

- `AET_PROJECT_ROOT` — Override project root for the on-disk checkpoint
  store (`<projectRoot>/.aet/core-checkpoint/`). The handler sets this
  from the hook input's `cwd` field when spawning the CLI in active
  mode. In passive mode the agent's Bash CWD is used as-is.
- `AET_GLOBAL_ROOT` — Override global root (for the global template
  workflow config). Defaults to `os.homedir()`.
- `AET_BIN` — Override the `aet` CLI binary path. Defaults to `aet`
  (resolved via `$PATH`).
